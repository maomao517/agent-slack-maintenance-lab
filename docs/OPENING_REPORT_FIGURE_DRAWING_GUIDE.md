# 开题报告配图绘制说明

本文档用于指导开题报告和开题PPT配图的绘制。图中不出现具体智能体框架名称和具体视觉语言模型名称。中文使用宋体，英文、数字和数学符号使用Times New Roman；中英文边界不加空格。

## 一、配图总览

建议最终保留以下4张补充图：

1.面向多模态文档分析智能体的时间感知状态管理架构图；
2.智能体暂停期间的恢复时间感知状态决策流程图；
3.不同并发度下的视觉编码避免率与跨任务命中率；
4.不同输入分辨率下完整视觉状态的实测容量。

其中，前两张说明拟研究系统和核心方法，后两张说明前置实验观察到的复用机会与资源代价。

## 二、图1：时间感知状态管理架构图

### 2.1建议图题

> 面向多模态文档分析智能体的暂停时长与恢复成本感知状态管理架构

也可以继续使用：

> 面向多模态文档分析智能体的恢复时间感知状态管理架构

第一种标题更准确地强调了本研究同时关注预计等待时间和状态恢复成本。

### 2.2整体布局

采用从左到右的五列布局：

```text
多模态文档任务
    →智能体工作流
    →恢复时间感知状态管理器
    →分层状态存储
    →多模态推理服务
```

状态管理器放在画面中心，宽度应大于其他模块。所有控制逻辑进入状态管理器，所有状态迁移从状态管理器发出，避免箭头直接穿过多个模块。

### 2.3第一列：多模态文档任务

外框标题：

```text
多模态文档任务
```

内部放置3类内容：

```text
文档页面
图表与公式
用户问题
```

下方单独列出任务元数据：

```text
页面标识
文档版本
任务标识
```

从该模块指向“智能体工作流”的箭头标注：

```text
任务输入
```

### 2.4第二列：智能体工作流

外框标题：

```text
智能体工作流
```

内部按照实际执行顺序自上而下排列：

```text
任务规划
↓
工具/环境调用
↓
等待外部结果
↓
整合工具结果并继续推理
```

“等待外部结果”使用虚线边框，内部标注：

```text
任务暂停窗口
```

不要将“多模态工具调用”作为唯一工具类型。智能体可以调用检索、代码执行、数据库和文档操作等外部工具，因此建议统一写为“工具/环境调用”。

### 2.5外部工具与执行环境

在智能体工作流下方增加独立模块：

```text
外部工具与执行环境
```

内部只放少量示例：

```text
检索｜代码执行｜数据库｜文档操作
```

连接关系必须明确：

```text
工具/环境调用→外部工具与执行环境
外部工具与执行环境→整合工具结果并继续推理
```

第一条箭头标注“调用请求”，第二条箭头标注“工具返回”。

### 2.6第三列：恢复时间感知状态管理器

外框标题：

```text
恢复时间感知状态管理器
```

内部使用4个编号模块。

#### 模块1：暂停窗口检测

标题：

```text
暂停窗口检测
```

内容：

```text
识别工具调用开始与结束
记录任务暂停时刻
```

#### 模块2：预计剩余等待时间估计

标题：

```text
预计剩余等待时间估计
```

输入特征：

```text
工具类型
已等待时间
历史执行时间
```

输出：

```text
预计剩余等待时间 T̂wait
```

这里的估计对象是工具或环境返回前的剩余等待时间，不是模型生成时间。

#### 模块3：状态成本与有效性分析

标题：

```text
状态成本与有效性分析
```

内容：

```text
页面版本有效性
状态大小
GPU显存压力
CPU传输时间
状态恢复时间
视觉重新编码时间
```

页面版本发生变化时，旧视觉状态应判定为失效，不能继续恢复。

#### 模块4：状态租约决策

标题：

```text
状态租约决策
（保留时限与层级）
```

内容：

```text
保留完整状态
下沉保存视觉状态
释放并等待重算
```

模块3与模块4之间增加一个判断框：

```text
迁移时间≤T̂wait
且
恢复成本<重新计算成本
```

该判断框用于突出本研究的核心思路：如果状态迁移能够在工具等待窗口内完成，且恢复成本低于重新计算成本，则优先将状态迁移到更合适的存储层级。

### 2.7第四列：分层状态存储

外框标题：

```text
分层状态存储
```

自上而下放置：

```text
GPU显存
完整KV cache+热视觉状态

CPU内存
跨任务共享视觉状态

本地存储
低频视觉状态
```

其中KV cache首次出现时在正文或图注中解释为：

```text
KV cache（key-value cache，键值缓存）
```

状态管理器到各层的箭头标注：

```text
GPU显存：保留/恢复
CPU内存：下沉/恢复
本地存储：下沉/恢复
```

GPU与CPU、CPU与本地存储之间可以使用双向虚线箭头，标注：

```text
下沉
上移
```

不要把管理器到本地存储的箭头标为“释放”。写入本地存储仍然是状态保留，只是存储层级降低。

在分层存储下方增加一个独立模块：

```text
状态释放
工具返回后重新计算
```

该模块表示真正不保留状态的情况。

### 2.8第五列：多模态推理服务

外框标题：

```text
多模态推理服务
```

这里不能画成固定的“视觉编码→状态恢复→语言模型推理”串行流程。正确结构是两条分支汇合：

```text
缓存未命中→视觉编码──┐
                     ├→语言模型推理
缓存命中→状态恢复────┘
```

语言模型推理之后输出：

```text
分析结果
证据页面
版本信息
```

推理服务与智能体工作流之间增加双向连接：

```text
智能体工作流→多模态推理服务：推理请求/工具结果
多模态推理服务→智能体工作流：模型输出/工具调用
```

### 2.9反馈流

建议拆分为两条紫色虚线反馈流：

```text
外部工具与执行环境
→预计剩余等待时间估计
实际工具耗时
```

```text
多模态推理服务与分层状态存储
→状态成本与有效性分析
实际编码、迁移与恢复耗时
```

底部图例只保留三类线：

```text
数据流｜控制流｜反馈流
```

### 2.10图1检查清单

- 是否明确画出外部工具与执行环境；
- 是否存在工具调用、任务暂停、工具返回和继续推理的完整链路；
- 是否明确表示缓存命中和未命中的两条推理路径；
- 是否将“下沉”与“释放”区分开；
- 是否出现`T̂wait`及迁移时间判断；
- 是否体现页面版本有效性检查；
- 是否存在推理服务与智能体工作流之间的双向连接；
- 是否没有具体框架名称和具体模型名称。

## 三、图2：恢复时间感知状态决策流程图

### 3.1建议图题

> 智能体暂停期间的恢复时间感知状态决策流程

### 3.2主流程

使用从上到下的流程图：

```text
智能体发起工具调用
↓
检测到任务暂停
↓
获取当前运行状态
↓
估计工具剩余执行时间
↓
检查页面版本是否有效
↓
比较迁移、恢复与重新计算成本
↓
选择状态管理动作
↓
工具返回
↓
恢复智能体推理
```

### 3.3运行状态输入框

在流程左侧或右侧增加数据输入框：

```text
工具类型
已等待时间
历史工具耗时
当前状态大小
GPU显存压力
页面及版本标识
视觉编码时间
状态迁移与恢复时间
```

### 3.4核心判断分支

按照以下逻辑绘制菱形判断框：

```text
页面版本是否有效？
├─否→释放旧状态→工具返回后重新编码
└─是
   ↓
预计等待时间是否较短且GPU空间充足？
├─是→保留完整状态
└─否
   ↓
迁移时间是否不超过预计剩余等待时间？
├─否→根据资源压力保留或释放
└─是
   ↓
视觉状态恢复是否快于重新编码？
├─是→下沉至CPU共享缓存或本地存储
└─否→释放状态
```

### 3.5工具返回后的三条路径

```text
完整状态仍在GPU
→直接恢复后续推理

视觉状态在CPU或本地存储
→加载视觉状态→恢复后续推理

状态已经释放
→重新执行视觉编码→恢复后续推理
```

三条路径最终汇入：

```text
记录实际等待、迁移、恢复和重算耗时
```

再反馈给预计时间估计器和状态成本分析器。

### 3.6图2图注

> 智能体进入工具等待窗口后，系统根据预计剩余等待时间、页面版本、当前资源压力以及迁移、恢复和重算成本选择状态层级。若迁移开销能够被等待窗口覆盖，且恢复成本低于重新计算成本，则优先下沉并在工具返回后恢复；否则保留或释放状态。

## 四、图3：编码避免率与跨任务命中率

### 4.1建议图题

> 不同并发度下的视觉编码避免率与跨任务命中率

采用左右两个子图：

```text
(a)视觉编码避免率
(b)跨任务命中率
```

横轴统一为并发任务数：`1、2、4、8`。

### 4.2子图(a)数据

纵轴：视觉编码避免率/%。

|并发数|Task-Local|SharedGPU|SharedCPU|SharedTieredGPUCPU|
|---:|---:|---:|---:|---:|
|1|30.0|30.0|30.0|30.0|
|2|30.0|35.0|28.8|35.0|
|4|30.0|33.8|26.9|32.5|
|8|30.0|31.3|24.4|31.6|

### 4.3子图(b)数据

纵轴：跨任务命中率/%。

|并发数|Task-Local|SharedGPU|SharedCPU|SharedTieredGPUCPU|
|---:|---:|---:|---:|---:|
|1|0.0|0.0|0.0|0.0|
|2|0.0|3.9|11.8|6.8|
|4|0.0|6.7|15.4|4.4|
|8|0.0|4.0|17.8|4.4|

### 4.4绘图形式

建议使用分组柱状图。若使用折线图，应保留数据点，不使用平滑曲线。

颜色统一为：

```text
Task-Local：蓝色
SharedGPU：红色
SharedCPU：绿色
SharedTieredGPUCPU：橙色
```

图例名称要与报告正文一致，不要混用`PerTask`和`Task-Local`。

### 4.5图3图注

> 编码避免率表示相对于理论页面访问次数未执行视觉编码的比例；跨任务命中率仅统计由其他任务产生并被当前任务复用的视觉状态。并发数为1时不存在跨任务共享机会。数据按页面重叠率聚合，并取20次正式重复实验的中位数。

### 4.6图3正文结论

> 缓存策略能够避免约24%至35%的视觉编码，说明多任务工作流中存在可观测的视觉状态复用机会。SharedCPU在并发数为4和8时的跨任务命中率分别达到15.4%和17.8%，但较高的跨任务命中率并未直接转化为最低请求时延。这表明命中率不能作为唯一优化目标，还需要同时考虑状态迁移、恢复和并发竞争成本。

## 五、图4：完整视觉状态容量

### 5.1建议图题

> 不同输入分辨率下完整视觉状态的实测容量

### 5.2数据

当前采用原图直接输入路径时，完整视觉状态实测值为：

|输入分辨率等级|完整视觉状态容量/MB|
|---|---:|
|低|7.875|
|中|30.375|
|高|67.906|

### 5.3绘图形式

- 使用单组柱状图；
- 横轴：输入图像分辨率等级；
- 纵轴：完整视觉状态容量/MB；
- 纵轴从0开始；
- 柱顶标注`7.875`、`30.375`和`67.906`；
- 不再绘制旧版2.5MB、9.375MB和38.75MB；
- 不再混入只包含`image_embeds`的基础嵌入容量。

### 5.4图4图注

> 完整视觉状态包括命中路径恢复一致推理所需的全部视觉中间状态。容量由实际缓存张量统计得到，并随输入处理后的视觉序列长度和图像数量增加而增长。

### 5.5图4正文结论

> 完整视觉状态容量随输入分辨率增加而明显增长。视觉状态虽然小于模型参数规模，但在多页面、多任务长期驻留时仍会形成不可忽略的存储开销。因此，系统需要在GPU显存、CPU内存和本地存储之间进行分层管理，并根据预计恢复时间和状态恢复成本选择保留层级。

## 六、统一绘图规范

### 6.1字体

- 中文：宋体；
- 英文、数字和数学符号：Times New Roman；
- 中文与英文之间不加空格；
- 缩写第一次在正文或图注出现时给出全称，图内尽量保持简洁。

### 6.2颜色

建议使用白色背景和低饱和学术配色：

```text
智能体工作流：蓝色
状态管理器：深蓝色
GPU显存：橙红色
CPU内存：绿色
本地存储：灰色
推理服务：紫色
数据流：黑色实线
控制流：黑色虚线
反馈流：紫色虚线
```

### 6.3文字控制

- 架构图中每个模块尽量不超过3行说明；
- 判断框只保留决策条件，不放长段落；
- 实验图中结论写入正文和图注，不在图内放大段解释；
- 所有图使用统一的“图题+图注+正文解释”结构；
- 不使用“阶段A、阶段B、阶段C、阶段D”作为正式图题或正文标题。

### 6.4开题报告中的推荐顺序

```text
图1：视觉编码瓶颈
图2：图像数量与视觉编码时间
图3：分层恢复与重新编码
图4：完整视觉状态容量
图5：并发请求时延
图6：编码避免率与跨任务命中率
图7：拟研究系统架构
图8：恢复时间感知决策流程
```

如果正文篇幅有限，优先保留图1、图3、图5、图7和图8；图4可放入研究方案或附录，图6可放入开题PPT备份页。

# 基于OpenCode的多轮文档图像分析智能体实验方案

## 1. 文档状态

本文档描述下一步实验的接入方式、最小工作负载、日志口径、对比策略和停止条件，用于补充真实智能体工作流证据。

前期实验已经完成Qwen3-VL性能剖析、视觉状态保存与恢复以及缓存策略验证；当前Git仓库还提供缓存策略回放和OpenAI兼容请求追踪等基础。本文提到的`doc_vlm_server.py`和`doc_tool.py`是下一步需要实现的OpenCode适配接口，**当前不是可直接执行的现有脚本**。

## 2. 实验目的

已有实验已经证明：

1. 文档页面的视觉编码在当前测试环境中构成主要计算开销；
2. 完整可复用视觉状态应包含`image_embeds`和3组DeepStack特征；
3. 从GPU显存、CPU内存或本地热文件恢复完整状态，明显快于重新执行视觉编码；
4. 完整状态恢复能够保持首步logits和贪心解码结果一致。

上述结果仍属于模型调用层面的瓶颈识别和技术可行性验证，尚不能证明真实智能体工作流中存在足够的页面回访和跨任务复用。本实验使用OpenCode作为工具调用智能体编排器，重点回答以下问题：

1. OpenCode在完成多文档证据分析任务时，是否会自主产生多轮工具调用和工具等待？
2. 同一工作流是否会再次访问相同页面？
3. 不同工作流是否会访问相同页面？
4. 页面复用距离和工具等待时间是否足以形成可管理的状态生命周期？
5. 在相同访问轨迹和缓存容量下，共享视觉状态是否能够减少视觉编码次数并改善平均JCT和P95 JCT？

## 3. 系统边界

### 3.1 推荐接入结构

```text
用户任务
  ->OpenCode规划并选择工具
  ->search_pages检索候选页面
  ->analyze_page请求页面理解
  ->常驻Qwen3-VL服务执行视觉编码或恢复视觉状态
  ->OpenCode调用calculate等后续工具
  ->OpenCode根据工具结果继续推理
  ->输出答案及证据页标识
```

OpenCode负责规划、工具选择和工作流推进；Qwen3-VL负责文档页面的多模态理解；缓存模块位于Qwen3-VL服务内部。实验不修改模型参数，也不要求修改OpenCode内核。

### 3.2 暂不纳入的内容

首轮实验不研究以下问题：

- OpenCode规划模型自身KV cache的保存与恢复；
- 等待时间预测模型；
- 训练或微调视觉语言模型；
- 大规模参数搜索；
- 复杂的GPU显存与主机内存联合优化；
- OpenCode内部调度器改造。

因此，首轮实验验证的是“真实智能体工作流中的视觉页面复用及共享编码器状态收益”，不是完整的智能体KV cache生命周期管理系统。

## 4. 接入前检查

应先在目标OpenCode环境中确认：

1. 是否允许智能体通过Shell执行仓库内的Python脚本；
2. 每个任务或会话的`session_id`如何获得；
3. 是否可以在启动任务时注入`RUN_ID`、`WORKFLOW_ID`和`TASK_ID`；
4. 是否支持非交互式批量执行任务；
5. 是否可以固定`temperature=0`或其他确定性参数；
6. 是否能够输出工具调用开始、结束、返回状态和任务完成时间；
7. 若使用原生工具接口，是否支持MCP（Model Context Protocol，模型上下文协议）或自定义工具注册。

只要第1、3和4项成立，就可以使用Shell适配方案，不需要等待MCP接入。

### 4.1 OpenCode 1.18.12实测结果

目标环境已经完成接口核验，结果如下：

|能力|实测结果|实验采用方式|
|---|---|---|
|执行仓库内Python脚本|支持|由OpenCode通过Shell调用`doc_tool.py`|
|任务与会话管理|支持|使用`--title`标记任务，从JSON事件或导出结果登记真实`session_id`|
|环境变量注入|支持|批处理入口注入`RUN_ID`、`WORKFLOW_ID`和`TASK_ID`|
|非交互式批量执行|支持|使用`opencode run --auto --format json`|
|固定解码参数|OpenCode命令行不直接提供|在模型服务层固定；主要策略比较使用固定轨迹回放|
|工具事件输出|支持|OpenCode JSON事件用于交叉验证，工具自身负责纳秒级计时|
|MCP与自定义工具|支持|首轮不使用，保留为后续结构化接入方案|

因此，首轮实验确定采用Shell适配路线。该路线不修改OpenCode内核，也不依赖MCP注册。

### 4.2 标识与会话规则

三个实验标识由批处理脚本生成并通过环境变量传递，以环境变量为唯一事实来源：

```text
RUN_ID       一次完整实验运行
WORKFLOW_ID  一个独立OpenCode工作流
TASK_ID      工作负载清单中的任务
```

`--title`只作为人工检查标签，不替代上述标识。OpenCode产生的真实`session_id`从`--format json`事件流或`opencode export`结果中提取，并单独保存映射：

```json
{
  "run_id": "run-001",
  "workflow_id": "workflow-001",
  "task_id": "task-001",
  "opencode_session_id": "..."
}
```

一个任务能够在单次`opencode run`中自主完成多次工具调用，因此首轮将“一个任务”映射为“一次OpenCode会话”。只有当任务确实需要由外部程序分多次追加消息时，才在首次调用后提取`session_id`，并使用`-s/--session`继续同一会话。

批处理命令草案如下：

```bash
RUN_ID="run-001" \
WORKFLOW_ID="workflow-001" \
TASK_ID="task-001" \
opencode run --auto --format json \
  --title "workflow-001-task-001" \
  "$TASK_PROMPT" \
  > artifacts/traces/opencode/run-001/task-001.events.jsonl
```

批处理程序还需在OpenCode进程外记录任务开始时间、结束时间、退出码和超时状态。提示词中可以说明工具使用规则，但不让模型自行生成或修改实验标识。

### 4.3 解码随机性的处理

OpenCode 1.18.12命令行不直接提供`temperature`参数。若模型服务由实验独占，可以在服务层固定`temperature=0`和其他采样参数；若无法修改服务配置，则采用以下方法控制影响：

1. 真实OpenCode执行只用于采集自然工具调用和页面访问轨迹；
2. 缓存策略的主要比较固定首次采集的页面访问顺序、工具时长、任务到达和并发关系；
3. 真实端到端复核报告任务成功率、工具序列差异和重复实验离散程度；
4. 不把不同OpenCode运行之间的单次JCT差异直接归因于缓存策略。

## 5. 待实现的最小适配接口

### 5.1 常驻视觉语言模型服务

建议新增：

```text
scripts/doc_vlm_server.py
```

职责包括：

- 启动时加载一次Qwen3-VL-8B-Instruct；
- 接收页面路径、页面版本、问题和工作流标识；
- 根据`image_sha256+document_version+model_config_hash`构造缓存键；
- 执行重新视觉编码或完整视觉状态恢复；
- 支持`no_cache`、`task_local`和`shared_cpu`三种最小策略；
- 将请求、编码、恢复、缓存命中和错误事件写入JSONL文件；
- 返回页面分析结果、证据描述和性能元数据。

接口示例：

```text
POST /analyze
POST /cache/clear
GET  /health
GET  /metrics
```

启动命令草案：

```bash
source envs/control/bin/activate

CUDA_VISIBLE_DEVICES=0 python scripts/doc_vlm_server.py \
  --model-dir "$MODEL_DIR" \
  --host 127.0.0.1 \
  --port 30200 \
  --cache-policy no_cache \
  --trace-output artifacts/traces/opencode-vlm.jsonl
```

服务只监听`127.0.0.1`，避免暴露到外部网络。

### 5.2 OpenCode工具客户端

建议新增：

```text
scripts/doc_tool.py
```

最小子命令：

```text
search     根据清单和关键词返回候选页面
analyze    请求常驻Qwen3-VL服务分析页面
calculate  对结构化数值执行受限计算
submit     校验最终答案是否包含证据页
```

调用示例：

```bash
python scripts/doc_tool.py analyze \
  --server http://127.0.0.1:30200 \
  --page-id M1 \
  --version v1 \
  --image data/public_docs/resized/medium/M1.png \
  --question "提取页面中的主要指标并给出证据位置"
```

客户端从环境变量读取`RUN_ID`、`WORKFLOW_ID`和`TASK_ID`，并将其传给服务端。工具标准输出只返回结构化JSON，诊断信息写入标准错误或独立日志，避免干扰OpenCode解析。

## 6. OpenCode任务约束

建议向OpenCode提供如下任务说明：

```text
你是一个多文档证据分析智能体。

你需要自主选择并调用仓库提供的search、analyze和calculate工具。
不得在未调用页面分析工具的情况下猜测页面内容。
当问题涉及多个页面时，先检索候选页面，再分析必要页面。
最终答案必须包含document_id、page_id和证据描述。
所有工具调用必须保留当前RUN_ID、WORKFLOW_ID和TASK_ID。
```

不能在提示词中直接给出需要访问的页面序列，否则只能得到脚本化回放，不能证明智能体自主产生了页面复用。

## 7. 工作负载设计

### 7.1 数据来源

优先从MMDocRAG或VisDoMBench选择具有公开证据页的多模态问题，并使用现有`public_docs`页面补充受控样例。页面应覆盖：

- 正文密集页面；
- 表格页面；
- 图表页面；
- 正文、表格和图形混合页面。

所有页面均使用公开、非敏感数据，保留来源、页码、版本和SHA-256哈希。

### 7.2 最小任务集

首轮使用12个任务，建议由4组文档构成，每组设计3个关联问题：

|任务类型|数量|目的|
|---|---:|---|
|同一文档内的多页面证据问题|4|观察工作流内部页面回访|
|围绕同一文档的不同问题|4|观察跨任务页面共享|
|无重叠文档问题|2|作为无复用负对照|
|文档版本变化问题|2|验证版本变化后缓存失效|

每个任务允许OpenCode自主决定工具调用次数，但目标是形成约3至4次页面分析或工具调用。若多数任务只发生一次页面分析，应先调整问题设计，不进入缓存策略比较。

## 9. 实验步骤

### 9.1 冒烟测试

使用1个任务确认：

- OpenCode能够自主执行至少两种工具；
- Qwen3-VL只加载一次；
- 页面分析结果能够返回OpenCode；
- 工具开始与结束时间完整；
- 页面哈希、版本和工作流标识均能落盘；
- 服务异常时OpenCode能够收到明确错误，而不是静默重试。

预计耗时约1小时，不形成论文结论。

### 9.2 真实智能体轨迹采集

固定`cache_policy=no_cache`运行12个任务，先使用并发度1，再使用并发度4。该实验用于测量自然产生的页面访问序列，重点输出：

- 每个任务的模型和工具调用次数；
- 工具等待时间分布；
- 工作流内页面复用率；
- 跨工作流页面复用率；
- 页面复用距离；
- 文档版本变化次数；
- 任务成功率和答案证据一致性。

该步骤预计运行1至3小时。

每个任务完成后保存两类原始记录：

```text
artifacts/traces/opencode/<run_id>/<task_id>.events.jsonl
artifacts/traces/opencode/<run_id>/<task_id>.session.json
```

第一类是`opencode run --format json`输出的事件流；第二类由`opencode export <session_id>`产生。两者仅用于追溯OpenCode决策和交叉验证工具事件，真实性能计时仍以`doc_tool.py`、Qwen3-VL服务和外层任务运行器记录为准。

### 9.3 固定轨迹缓存对比

将上一节采集的页面访问、工具时长、任务到达和并发关系转换为固定轨迹，在相同轨迹和容量下比较：

|策略|含义|
|---|---|
|NoCache|每次访问都重新执行视觉编码|
|Task-Local Cache|只允许同一工作流复用视觉状态|
|Shared CPU Cache|不同工作流共享CPU内存中的完整视觉状态|

每种策略至少重复3次，记录平均值、中位数、P95和离散程度。主要指标包括：

- 视觉编码调用次数；
- 工作流内命中率；
- 跨工作流命中率；
- 平均JCT；
- P95 JCT；
- 吞吐量；
- 峰值GPU显存；
- 主机到设备传输量；
- 过期状态误命中次数；
- 答案和证据一致性。

该步骤预计运行3至6小时。

### 9.4 真实端到端复核

固定轨迹回放能够保证公平性，但不能完全代替真实智能体执行。若共享缓存在回放中产生稳定收益，再分别使用`no_cache`和`shared_cpu`运行完整OpenCode任务。

端到端复核固定：

- 任务集合；
- 系统提示词；
- 模型与版本；
- 解码参数；
- 页面集合；
- 并发度；
- 缓存容量。

由于OpenCode可能在不同运行中选择不同工具，真实端到端结果作为外部有效性证据；主要策略比较仍以固定轨迹回放为准。

## 10. 最小实验矩阵与预计时长

建议开题前只完成以下矩阵：

```text
任务数：12
平均页面或工具调用：3至4次/任务
策略：NoCache、Task-Local Cache、Shared CPU Cache
重复次数：3
并发度：1和4
```

中等分辨率页面重新视觉编码约为18秒。若每个任务发生4次页面访问，则全部未命中时每轮纯视觉计算时间约为：

```text
12×4×18秒=864秒，约14.4分钟
```

考虑OpenCode规划、工具调用、模型生成、服务启动和调度开销，预计时间如下：

|工作内容|预计时间|
|---|---:|
|接口检查和冒烟测试|约1小时|
|实现常驻服务和工具客户端|0.5至1个工作日|
|无缓存真实轨迹采集|1至3小时|
|三种缓存策略重复实验|3至6小时|
|并发度补测和结果核验|2至4小时|

在现有视觉状态代码能够复用的条件下，最小实验通常可在1至2天内完成。若需要修改OpenCode内核或推理后端，则不再属于当前最小方案。

## 11. 结果判定与停止条件

### 11.1 支持继续研究的证据

同时满足以下条件时，继续研究跨任务共享和分层状态管理：

1. OpenCode工作流中存在可重复观测的多轮工具调用；
2. 多个任务访问相同页面，且跨工作流复用率不为偶然单例；
3. Shared CPU Cache相对于Task-Local Cache进一步减少视觉编码次数；
4. 平均JCT或P95 JCT的改善超过重复实验波动；
5. 缓存命中不改变答案和证据页；
6. 版本变化时不存在过期状态误命中。

### 11.2 收窄研究范围

出现以下情况时，不实现复杂分层策略：

- 只有工作流内部复用，没有跨工作流复用：研究收窄为任务内视觉状态缓存；
- Shared CPU Cache已经稳定取得最优结果：研究收窄为共享视觉状态存储和淘汰；
- 固定容量下简单LRU已经接近Oracle：不增加等待时间预测和复杂租约；
- GPU显存层相对CPU内存没有可观测收益：不把GPU内淘汰作为核心创新。

### 11.3 停止该路线

出现以下情况时，应停止缓存路线或更换应用场景：

- 多数OpenCode任务只访问一个页面一次；
- 页面回访主要来自提示词强制指定，而不是任务需要；
- 视觉编码节省无法转化为JCT或吞吐量改善；
- 状态恢复不能稳定保持输出和证据一致；
- OpenCode框架无法提供基本任务标识和工具事件记录。

## 12. 开题报告中的使用边界

完成真实轨迹采集后，可以在开题报告中表述：

> 本研究基于工具调用智能体框架构建多文档证据分析工作负载，记录模型推理、页面检索、视觉分析、数值计算及工具等待事件，用于测量页面回访、跨任务复用和视觉状态生命周期。

只有固定轨迹和真实端到端结果均支持时，才能进一步表述：

> 跨任务共享视觉状态减少了重复视觉编码，并在相同工作负载、缓存容量和并发条件下改善了任务完成时间。

在结果完成前，不能声称共享缓存已经降低P95 JCT，也不能将OpenCode框架本身作为本文创新点。

## 13. 环境与数据约束

- 所有依赖安装在仓库内虚拟环境，不使用系统级安装；
- 模型与数据均通过本地路径读取，实验运行不依赖外网；

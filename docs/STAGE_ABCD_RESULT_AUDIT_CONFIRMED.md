# 阶段A至D实验结果口径核验结论（审校稿）

## 1. 核验目的与依据

本次核验面向2026年8月14日更新实验脚本后生成的阶段A至D结果，重点确认视觉输入规模、完整可复用状态、缓存命中计时和多轮轨迹统计4项口径。

核验直接读取以下实验脚本和结果文件，不依据报告文字反推实现：

```text
scripts/profile_local_vlm.py
scripts/stage_c_cache_validation.py
scripts/stage_d_agent_trajectories.py
results/profiling/results_full.json
results/cache/cache_experiment_results.json
results/agent_trajectories/trajectory_results.json
```

关键分辨率、视觉序列长度和状态结构通过处理器与模型单卡实测复核。核验结果表明，原报告的4项口径均需要不同程度的修正。

## 2. 视觉输入规模字段

### 2.1 核验结论

阶段B中的491,520、1,843,200和7,618,560不是视觉token数，也不是单一图像的像素数，而是处理器输出张量`pixel_values`的元素总数：

```text
pixel_values.numel()
=pixel_values.shape[0]×1536
```

脚本虽然将该字段命名为`vision_token_count`，但变量名称与实际含义不一致。正式报告应将其改为“视觉输入张量元素数”或直接删除，不能继续称为视觉token数。

### 2.2 实际视觉序列长度

Qwen3-VL在视觉编码器末端使用2×2空间合并，`spatial_merge_size=2`。语言模型实际接收的视觉序列长度为：

```text
image_grid_thw.prod(-1)/spatial_merge_size²
```

实测结果如下：

|分辨率|`pixel_values`形状|张量元素总数|`image_grid_thw`|合并前网格数|实际视觉token数|
|---|---:|---:|---:|---:|---:|
|低|`(320,1536)`|491,520|`[1,20,16]`|320|80|
|中|`(1200,1536)`|1,843,200|`[1,40,30]`|1,200|300|
|高|`(4960,1536)`|7,618,560|`[1,80,62]`|4,960|1,240|

因此，阶段B图表应使用80、300和1,240作为实际视觉token数。原字段491,520、1,843,200和7,618,560可以保留为处理器输入张量规模，但不适合作为横轴上的视觉token数量。

## 3. 基础视觉嵌入与运行时完整状态

### 3.1 状态结构

`get_image_features`返回：

```text
(image_embeds, deepstack_image_embeds)
```

其中，`image_embeds`进入语言模型的基础视觉表示；`deepstack_image_embeds`包含视觉编码器第8、16和24层的3组特征，并在文本模型对应层通过`_deepstack_process`注入隐藏状态。

阶段C的真实命中路径同时保存并恢复两部分状态：

```text
{
  image_embeds_tuple: ...,
  deepstack_embeds: ...
}
```

命中时，`inject_encoder_hit`返回缓存中的`image_embeds`和全部`deepstack`特征，而不是只恢复`image_embeds`。

### 3.2 两种状态大小口径

阶段A、B的统计目标是观察基础视觉嵌入随输入规模的变化，因此脚本有意只统计`image_embeds`，不把`deepstack`计入`cache_size_mb`。在这一统计定义下，中等分辨率的基础视觉嵌入大小为2.3438MB。该数值是阶段A、B直接报告的实验指标，口径本身没有错误，但不应称为“核心缓存大小”，建议将字段名称明确为：

```text
image_embeds_size_mb
```

阶段C研究的则是能够正确恢复模型执行的实际缓存对象。由于真实命中路径同时保存`image_embeds`和3组`deepstack`特征，因此还需要单独给出运行时完整状态大小。原结果文件没有直接报告9.375MB这一字段；下表根据核验得到的张量形状、元素数量和BF16每元素2字节的口径计算该派生值。

|张量|形状|数据类型|元素数量|大小|
|---|---:|---:|---:|---:|
|`image_embeds`|`(300,4096)`|BF16|1,228,800|2.3438MB|
|`deepstack_layer8`|`(300,4096)`|BF16|1,228,800|2.3438MB|
|`deepstack_layer16`|`(300,4096)`|BF16|1,228,800|2.3438MB|
|`deepstack_layer24`|`(300,4096)`|BF16|1,228,800|2.3438MB|
|运行时完整状态合计|4个张量|BF16|4,915,200|9.375MB（派生值）|

因此，两种指标不能混用：

```text
阶段A、B基础视觉嵌入：2.3438MB（直接统计值）
阶段C运行时完整状态：9.375MB（根据实际缓存张量计算的派生值）
```

按照相同张量结构推算，低、中、高分辨率的运行时完整状态分别约为2.5MB、9.375MB和38.75MB，随合并后的视觉token数线性增长。这3个完整状态大小均应标为派生值，而不是阶段A、B原始结果中的`cache_size_mb`。

### 3.3 `deepstack`消融结果

补充实验只恢复`image_embeds`，并将`deepstack`分别设置为`None`和全零张量。两种条件均满足视觉编码器调用次数为0，但得到：

```text
最大logits绝对误差：34.8125
贪心解码结果：与完整状态不一致
```

因此，只恢复2.3438MB的`image_embeds`会改变模型输出。阶段A、B可以继续使用2.3438MB描述基础视觉嵌入，但如果要估算阶段C真实命中路径的存储容量、加载开销和层级放置，就必须计入3组`deepstack`。中等分辨率的运行时完整状态应使用9.375MB这一派生值。

### 3.4 `deepstack`最小补充统计

`deepstack`需要纳入空间统计，但不需要重新运行阶段A、B完整性能矩阵。张量大小由形状、元素数量和数据类型唯一决定，同一分辨率下重复运行不会改变该数值。低、中、高3档各记录一次即可：

|分辨率|视觉token数|`image_embeds_size_mb`|`deepstack_count`|`deepstack_size_mb`|`reusable_state_size_mb`|
|---|---:|---:|---:|---:|---:|
|低|80|0.625|3|1.875|2.500|
|中|300|2.3438|3|7.0312|9.375|
|高|1,240|9.6875|3|29.0625|38.750|

三个字段的含义分别为：

```text
image_embeds_size_mb：阶段A、B直接统计的基础视觉嵌入大小
deepstack_size_mb：3组deepstack特征的大小之和
reusable_state_size_mb：阶段C正确恢复所需的全部视觉张量大小
```

建议脚本按照真实缓存对象统计：

```python
image_embeds_bytes = tensor_bytes(image_embeds)
deepstack_bytes = tensor_bytes(deepstack_embeds)
reusable_state_bytes = image_embeds_bytes + deepstack_bytes

result.update(
    {
        "image_embeds_size_mb": image_embeds_bytes / 1024**2,
        "deepstack_size_mb": deepstack_bytes / 1024**2,
        "reusable_state_size_mb": reusable_state_bytes / 1024**2,
    }
)
```

现阶段不需要单独测量`deepstack`计算时间。`image_embeds`和`deepstack`由同一次视觉编码产生，当前缓存路径也将二者作为一个完整恢复对象。开题报告只需补充其空间占用，并在CPU、GPU和文件后端的保存、加载与容量分析中使用`reusable_state_size_mb`。

## 4. 分层缓存恢复时间

### 4.1 当前计时边界

阶段C中的`avg_hit_elapsed_ms≈0.29s`不包含`cache.load()`，只覆盖状态已经加载后、注入缓存视觉特征的语言模型前向过程。

实际执行顺序为：

```text
cache.load()
->run_encoder_hit_path()
->缓存后语言模型前向
```

`cache.load()`在命中计时器开始前单独执行，其耗时没有计入`avg_hit_elapsed_ms`。因此，0.29s不能直接称为CPU或文件后端的端到端命中时间。

### 4.2 按现有分项测量估算的恢复时间

|后端|冷执行|状态加载|缓存后前向|估算端到端命中|估算加速比|
|---|---:|---:|---:|---:|---:|
|GPU|18,651.4ms|0.0395ms|293.996ms|约294.04ms|约63.4倍|
|CPU内存|19,245.9ms|235.32ms|293.904ms|约529.22ms|约36.4倍|
|本地热文件|17,980.7ms|248.48ms|292.638ms|约541.12ms|约33.2倍|

加速比统一按以下公式计算：

```text
speedup=cold_wall_ms/end_to_end_hit_wall_ms
```

当前数据可以支持“GPU、CPU内存和本地热文件恢复均显著快于重新执行视觉编码”，但不能再写“三种存储层级均获得63至65倍端到端加速”。

### 4.3 尚需补充的同步计时

冷路径和命中路径使用`time.perf_counter()`记录CPU墙钟时间，但计时窗口前后没有显式调用`torch.cuda.synchronize()`。正确性检查中的`.item()`会触发隐式同步，但发生在计时窗口之外。因此，当前端到端时间仍属于分项近似值，不能排除GPU异步执行造成的低估。

只需补做一次最小复测：

```text
torch.cuda.synchronize()
start=time.perf_counter()
cache.load()
cached_forward()
torch.cuda.synchronize()
end=time.perf_counter()
```

分别对GPU、CPU内存和本地热文件重复至少20次，即可得到可直接用于开题图表的端到端恢复时间。无需重新运行阶段B完整矩阵。

### 4.4 文件后端口径

文件后端在同一实验循环中反复读取同一临时文件，首次读取后文件进入操作系统页缓存。因此，约248.48ms表示本地热文件读取和反序列化，不代表物理磁盘冷读。

正式表述应为：

> 本地热文件读取与反序列化路径显著快于视觉重算。

公司环境无需为了开题报告执行需要管理员权限的页缓存清理操作。

## 5. 阶段D命中率与工作流耗时

### 5.1 实际统计口径

每类轨迹包含3个工作流，每个工作流执行4轮，共12次图像访问。命中率定义为：

```text
cache_hit_rate=cache_hits/12
```

阶段D使用单个全局`VisionStateCache`实例：

- 不同工作流共享缓存；
- 不同轨迹类型也共享缓存；
- 工作流或轨迹切换时不清空缓存；
- 缓存键为`(page_id,version,resolution)`；
- 没有额外预热轮次。

因此，后续工作流的首轮可能命中此前工作流或此前轨迹留下的状态。83%、58%、50%和33%不是脚本计算错误，而是全局共享缓存条件下的结果。

### 5.2 轨迹结果

|轨迹|工作流数|每工作流轮数|总访问数|命中数|未命中数|命中率|平均工作流JCT|
|---|---:|---:|---:|---:|---:|---:|---:|
|Same-Image|3|4|12|10|2|83.3%|13.820s|
|Page-Revisit|3|4|12|7|5|58.3%|32.253s|
|Version-Change|3|4|12|6|6|50.0%|43.352s|
|All-Distinct|3|4|12|4|8|33.3%|53.508s|

表中的13.820s、32.253s、43.352s和53.508s是3个工作流的JCT均值，每个JCT覆盖4轮执行，不是单轮平均时延，也不是P95 JCT。阶段D每类只有3个JCT样本，未计算P95。

### 5.3 跨工作流共享的初步证据

阶段D已经出现不同工作流之间的缓存命中。例如：

```text
same_image_2首轮命中same_image_1生成的M1状态；
all_distinct_2首轮命中all_distinct_1生成的C3状态；
all_distinct_3命中此前缓存中的T1、C3和M1状态。
```

这说明当前实现已经支持跨工作流共享，能够作为“跨任务共享可实现”的初步证据。但是，阶段D没有比较Shared Cache与Per-Task Cache，也没有控制页面重叠率和轨迹执行顺序，因此不能据此声称共享缓存已经显著降低P95 JCT。

### 5.4 当前阶段D的混杂因素

全局缓存跨轨迹类型持续存在，使不同轨迹的命中率和JCT受到执行顺序及历史缓存内容影响。由此产生两个限制：

1.四类轨迹之间不是完全独立的受控比较；
2.当前结果混合了工作流内部复用、跨工作流复用和跨轨迹历史命中。

如果要把四类轨迹的JCT差异作为正式对比图，应在每种轨迹类型开始前清空缓存，并将“共享缓存”和“任务隔离缓存”分别运行。现有结果可以作为可行性观察，但不宜用于因果归因。

### 5.5 `encoder_calls`字段异常

原汇总中每类轨迹的`encoder_calls`均为12，与未命中数2、5、6和8不一致。如果命中路径确实跳过视觉编码，则实际视觉编码次数应与缓存未命中次数一致。

因此，当前`encoder_calls`字段可能记录了总轮次或模型调用次数，而不是真实视觉编码器调用次数。正式报告应暂时删除该字段，或在每轮记录中使用视觉模块钩子重新统计：

```text
encoder_called=true/false
```

这项问题不影响缓存命中率的分子和分母，但会影响“减少了多少次视觉编码”的直接统计。

## 6. 最终核验结论

|核验事项|最终结论|报告处理|
|---|---|---|
|491,520等是否为视觉token数|否，为`pixel_values`元素总数|改用80、300和1,240作为视觉token数|
|阶段A、B基础视觉嵌入是否为2.34MB|是，统计口径有意不含`deepstack`|保留为`image_embeds_size_mb`|
|阶段C运行时完整状态是否只有2.34MB|否，真实命中还恢复3组`deepstack`特征|另列9.375MB派生值|
|0.29s是否包含加载|否，只包含缓存后前向|CPU约529ms、热文件约541ms，仍需同步墙钟复测|
|阶段D命中率为何高于空缓存理论值|不同工作流和轨迹共享同一个全局缓存|命中率本身可解释，但存在执行顺序混杂|
|阶段D是否已有P95 JCT|没有|P95留到阶段D2或增加重复后计算|
|阶段D是否证明跨任务共享优于任务内缓存|没有|只证明共享可实现，尚缺受控基线比较|

## 7. 对开题报告的影响

### 7.1 可以直接使用的结论

1.视觉编码是当前模型前向过程中的主要时延来源；
2.实际视觉token数由80增加至1,240时，视觉编码时间由4.82s增加至74.88s；
3.阶段A、B直接统计的基础视觉嵌入在中等分辨率下为2.3438MB；阶段C实际命中对象还包含3组`deepstack`特征，根据张量结构计算的运行时完整状态约为9.375MB；
4.完整视觉状态可以被真实恢复，命中路径跳过视觉编码器，并保持logits和贪心解码结果一致；
5.GPU、CPU内存和本地热文件恢复均明显快于重新进行视觉编码；
6.当前系统已经观察到跨工作流共享命中，但其相对于Per-Task Cache的收益仍需受控实验验证。

### 7.2 暂不使用的结论

以下表述在补充同步计时或受控对比前不进入开题报告：

```text
三种后端均获得63至65倍端到端加速；
阶段C运行时完整缓存对象只有2.34MB；
10%显存预算可以保存665个完整视觉状态；
阶段D的图像复用使工作流JCT降低74%；
阶段D已经证明Shared Cache降低P95 JCT；
阶段D的encoder_calls等于真实视觉编码次数。
```

若只讨论阶段A、B的基础`image_embeds`统计口径，10%理论空间约能容纳665个中等分辨率基础视觉嵌入；若讨论阶段C真实命中路径保存的运行时完整状态，则根据9.375MB派生值估算约能容纳166个。报告必须根据所讨论的缓存对象选择对应容量，不能把两种口径混写。完整状态规模仍足以支持当前12页实验，但在多租户或高分辨率场景下可能形成容量竞争。

## 8. 最小后续工作

当前不需要重新运行阶段A至D完整矩阵，只需完成两项最小工作：

1.在GPU、CPU内存和本地热文件恢复路径前后增加显式CUDA同步，得到单一墙钟覆盖的端到端恢复时间；
2.阶段D2采用独立运行的NoCache、Per-Task Cache和Shared Cache，固定页面重叠率与并发数，并在每个条件开始前清空缓存。

第一项用于固定开题报告中的分层恢复图；第二项可以作为跨任务共享的增强证据，但不是撰写开题报告前的必要条件。

# 跨任务共享视觉状态缓存实验：结果审计与补充测量清单

## 1. 文档目的

本文档审计2026年8月15日完成的真实并发跨任务共享缓存实验。实验原始结果记录于`results/d2/d2_results.json`，覆盖120个条件：4档并发、5档页面重叠率和6种缓存策略。

审计目标是明确：哪些结果能够作为开题报告的前置证据，哪些结论必须补齐正确性和计时口径后才能使用，以及以最小代价补齐哪些实验。

研究对象暂定为：**面向多模态智能体跨任务复用的恢复时间感知视觉状态管理系统**。

## 2. 已完成实验及其价值

### 2.1 实验设置

|项目|设置|
|---|---|
|模型|Qwen3-VL-8B-Instruct，FP16推理|
|数据|`public_docs`公开文档图像集，覆盖正文、表格、图表和混合页面|
|并发|1、2、4、8|
|页面重叠率|0%、25%、50%、75%、100%|
|缓存策略|NoCache、PerTask、SharedGPU、SharedCPU、SharedTieredGPUCPU、SharedCoalesced|
|重复|每条件预热5次，正式重复20次；每次含4轮页面访问|
|缓存键|`image_hash|doc_version|model_rev|proc_hash|vis_cfg_hash`|
|版本检查|包含1次版本失效测试|

任务提示词不进入视觉状态缓存键。这一设计合理：不同文本任务可以共享同一图像的视觉编码结果，但提示词相关的语言模型键值缓存不能据此共享。

### 2.2 已获得的有效证据

在并发为4的聚合记录中，单页冷视觉编码平均耗时为4992.1ms，而缓存视觉状态后的语言模型前向平均为195.7ms，前者约为后者的25.5倍。重复视觉编码是主要时延来源。

|观察|报告数值|可支持的判断|
|---|---:|---|
|NoCache平均处理时延|约5.12至5.19s|冷视觉编码主导单页处理时间|
|PerTask平均处理时延|约3.66至3.68s|任务内复用可将平均处理时延降低约29%|
|NoCache对PerTask加速比|约1.40至1.41倍|缓存机制具备明确的可行性收益|
|缓存策略编码避免率|overlap均值约24%至35%|缓存确实减少了视觉编码调用|
|总视觉编码时间下降|约30%至34%|编码避免与平均时延改善一致|
|高重叠条件下编码避免率|最高75%|页面复用密度决定缓存收益上界|

相对任务内缓存，跨任务共享也出现了增量收益。按重叠率均值计算，SharedGPU相对PerTask在并发为2、4、8时的平均处理时延分别额外降低约6.9%、4.6%和2.2%。这说明不同任务访问部分相同页面时，跨任务复用并非纯粹的模拟假设。

### 2.3 不能夸大的结果

1. P95时延改善不稳定，幅度多在0.5%至4%。当前实验支持“平均时延可下降”，不支持“共享缓存已稳定降低尾部时延”。
2. SharedCPU在高并发下的跨任务命中率较高，例如并发为8时的重叠率均值为17.8%，但其平均处理时延反而高于SharedGPU。命中率高不等价于端到端收益高。
3. SharedCoalesced没有观察到相对其他共享策略的显著重复编码抑制，所有策略的`duplicate_encoder_calls_median`均为0。当前工作负载没有形成足够的同时未命中，不应将请求合并写成已验证的优化点。

## 3. 必须补齐的口径与正确性检查

### 3.1 P0：完整视觉状态是否被真正缓存和恢复

此前的正确性核验已经确认，Qwen3-VL的视觉状态由`image_embeds`和3组`deepstack_image_embeds`共同组成。只恢复`image_embeds`会导致最大logits绝对误差达到34.8125，且贪心输出改变。因此，完整状态缺少任一deepstack特征都不能称为无损缓存。

本次结果报告中的low分辨率`vision_state_mb=0.625MB`，数值恰好等于单独`image_embeds`的大小。按此前已核验的状态结构，low分辨率完整可复用状态应为：

|分辨率|基础视觉嵌入|3组deepstack|完整可复用状态|
|---|---:|---:|---:|
|低|0.625MB|1.875MB|2.500MB|
|中|2.3438MB|7.0312MB|9.375MB|
|高|9.6875MB|29.0625MB|38.750MB|

必须直接检查D2的`save/load/inject`实现。只有确认每个策略都保存并恢复`image_embeds+deepstack`后，才能将D2结果用于无损视觉状态缓存的性能结论。

**验收条件：**

```text
cached_image_embeds=true
cached_deepstack_count=3
encoder_calls_on_hit=0
max_abs_logit_error<=数值误差阈值
greedy_output_equal=true
```

若D2只保存了`image_embeds`，需先修正缓存对象，再重跑全部120个条件；此前D2的时延和容量数据只能作为不完整状态跳过编码的调试记录，不能进入报告正文。

### 3.2 P0：答案一致性尚未验证

全部120个条件的`answer_consistency=0.0`表示该字段没有开启逐答案对比，而非“输出完全一致”。因此不能写“缓存命中不影响模型结果”。

不需要为此重复整套性能矩阵。应从每种策略至少抽取一个GPU命中、一个CPU命中和一个失效重算样本，记录：

```text
完整冷路径输出
缓存命中路径输出
max_abs_logit_error
greedy_output_equal
生成答案是否完全相同
```

### 3.3 P0：JCT的统计单位需要重新命名或补采

报告中的NoCache均值约为5.1s，接近一次冷视觉编码的时间；而每个工作流包含4轮访问。该指标很可能是单页请求时延或单轮时延，而不是完整智能体工作流的完成时间。

在确认原始字段前，文档和图表应使用“平均请求时延”“P95请求时延”而不是“平均JCT”“P95 JCT”。若希望使用工作流完成时间作为核心指标，必须记录：

```text
workflow_start_ns
workflow_end_ns
workflow_jct_ms=workflow_end_ns-workflow_start_ns
```

并按照一个工作流的多轮访问汇总JCT，再计算不同工作流样本的平均值、P50、P95和置信区间。

### 3.4 P1：SharedCPU的传输开销解释缺少证据

报告中SharedCPU的`cpu_to_gpu_transfer_ms`在所有重叠率下均为0，但文字将其平均处理时延偏高归因于CPU到GPU传输。这一因果解释目前不成立。

SharedCPU与SharedGPU在并发为4时的平均处理时延相差约375.6ms，远大于报告中11至18ms的GPU到CPU回存时间。更可能的来源包括CPU层命中后的恢复逻辑、额外未命中造成的重算、替换、锁竞争或并发等待。

必须在显式`torch.cuda.synchronize()`包围的同一墙钟窗口内分别记录：

```text
lookup_ms
gpu_to_cpu_save_ms
cpu_deserialize_ms
cpu_to_gpu_restore_ms
state_inject_ms
cached_forward_ms
queue_wait_ms
encoder_ms
```

### 3.5 P1：并发与存储拓扑需要写清楚

报告描述“每并发绑定一张GPU，各加载一个模型副本”。在这一拓扑下，单张GPU上的视觉状态不能自然跨GPU共享。需要明确：

1. `SharedGPU`是同一GPU内不同工作流共享，还是跨GPU搬运状态；
2. `SharedCPU`是否是不同模型副本可访问的真正进程间或节点内共享存储；
3. 跨GPU状态恢复是否发生设备间传输，以及传输是否计入端到端时延。

在未实现跨GPU状态搬运前，建议将`SharedGPU`表述为“每卡热缓存”，不要写成“跨任务全局GPU共享缓存”。跨任务全局复用更适合由CPU共享层承担。

### 3.6 P2：请求合并需要碰撞压力工作负载

当前所有策略的重复编码中位数为0，说明测试未让多个任务在同一时刻访问同一个未缓存页面。要评估请求合并，应增加一个同步屏障条件：让多个任务同时请求同一张尚未缓存的页面，并记录：

```text
inflight_waiter_count
duplicate_encoder_calls
coalescing_wait_ms
first_result_ready_ms
all_waiters_ready_ms
```

## 4. 当前数据在开题报告中的使用边界

### 4.1 经P0检查通过后可使用的表述

> 在公开文档页面构成的并发多任务工作负载中，视觉编码的时间开销显著高于缓存状态恢复后的语言模型前向。任务内缓存已能减少重复视觉编码并降低平均请求时延；当不同任务存在部分页面重叠时，共享缓存相对任务内缓存具有额外的平均时延收益。与此同时，现有静态共享策略对P95时延的改善有限，且不同缓存层级呈现命中率与端到端时延不一致的权衡。

该表述只陈述已有数据能够支撑的观察，不预设任何新策略必然优于所有基线。

### 4.2 在P0检查完成前不得使用的表述

```text
视觉状态仅需0.625MB
所有缓存策略均保持答案一致
SharedCPU因CPU到GPU传输而变慢
SharedCoalesced已抑制并发缓存击穿
共享缓存已显著降低P95 JCT
SharedGPU是跨GPU全局共享缓存
```

## 5. 后续方案的准确切入点

当前实验不应简单导向“扩大缓存容量”。真正可进一步研究的问题是：**在状态完整性受约束的前提下，系统应如何根据预计恢复时间、预计复用机会和当前资源压力，在GPU热缓存、CPU共享缓存与重算之间选择状态位置和保留期限。**

可将一次决策定义为比较：

```text
T_recompute
T_restore_gpu
T_restore_cpu
P_reuse_within_lease
GPU_pressure
queue_delay
```

预计恢复时间可以避免静态TTL带来的两类错误：将短期内会被复用的状态过早逐出，或长期占用GPU空间却迟迟未被再次访问。当前D2验证的是这一策略面对的性能不均衡和层级权衡，因而应定位为动机与基线实验，而非最终策略的验证。

## 6. 最小补实验清单与决策规则

|优先级|补测|规模|通过条件|未通过时的处理|
|---|---|---|---|---|
|P0|完整状态与输出一致性|6种策略各抽样3条路径|恢复3组deepstack且输出一致|修复状态对象并重跑D2|
|P0|请求时延与工作流JCT口径|从原始记录复核或补采工作流边界|指标名称和分母可复现|改名为请求时延，不使用JCT|
|P1|CPU分项恢复计时|SharedCPU和Tiered各覆盖命中与未命中|CPU到GPU传输、等待和前向均可解释|不对CPU慢的原因作因果归因|
|P1|并发拓扑核验|记录每个请求的GPU、进程和缓存所有者|明确共享范围|收缩SharedGPU的结论范围|
|P2|请求合并碰撞压力|同页同步到达的微基准|能产生可控重复编码|将Coalesced保留为候选机制|

完成P0检查后即可使用D2的核心趋势撰写开题报告；P1和P2用于完善系统设计和后续论文实验。若P0显示缓存对象不完整，则应暂停对D2性能数据的解释，先修复正确性，再重跑。
